# 4Story Portal: Design

Date: 2026-10-31
Status: awaiting review

## 1. Goal

A small web portal for a private 4Story server used by about 5 people over a VPN. It lets a player:

1. **Register** a game account (username + password) that works in the game client.
2. **Log in** to the portal with the same credentials as the game.
3. **See their characters** with basic info after logging in.

Out of scope for this version: password change or reset, character editing, admin tools, rankings, deployment beyond running locally, end-to-end tests.

## 2. Constraints from the game

These come from the game's source code and database and cannot be changed by the portal.

- **Database server:** SQL Server 2022 Express, instance `localhost\FOURSTORY`, TCP enabled on port 1433, mixed authentication.
- **Accounts:** `TGLOBAL_GSP.dbo.TACCOUNT_PW`.
  - `dwUserID int IDENTITY` (generated by the database).
  - `szUserID varchar(50) NOT NULL`: the username.
  - `szPasswd varchar(255)`: **lowercase hex SHA-1 of the password, unsalted**. The game client hashes the password with SHA-1 (`CTClientGame::GetSHA1String`) and the `TLogin` stored procedure compares the received string to `szPasswd` exactly.
  - `bCheck tinyint` (existing accounts have `0`).
- **Account agreement row:** `TGLOBAL_GSP.dbo.TUSERINFOTABLE` (`dwUserID`, `bCanCreateCharCount`, `bAgreement`, `dCabinetUse`). `TLogin` returns error 8 and the game login fails unless a row with `bAgreement = 1` exists. All existing accounts have `bAgreement = 1`, `bCanCreateCharCount = 6`.
- **Characters:** `TGAME_GSP.dbo.TCHARTABLE`, keyed to the account by `dwUserID`. Deleted characters have `bDelete <> 0`.
- **Encoding:** the client hashes the password as ANSI bytes, so passwords must be printable ASCII for web and game hashes to match.
- **The portal must never call `TLogin`.** It inserts a `TCURRENTUSER` row, which would make the player's next game login fail with "duplicate".
- **Code-to-name mappings** (from `Lib/Own/TProtocol/include/NetCode.h`):
  - Class (`bClass`): 0 Warrior, 1 Ranger, 2 Archer, 3 Wizard, 4 Priest, 5 Sorcerer.
  - Race (`bRace`): 0 Human, 1 Beast, 2 Nymph.
  - Country (`bCountry`): 0 Defugel (`TCONTRY_D`), 1 Craxion (`TCONTRY_C`), 2 `TCONTRY_B`, 3 `TCONTRY_N`, 4 Peace. The display names for 2 and 3 are confirmed during implementation; until then they show as "Country B" and "Neutral".
  - Unknown codes display as `Unknown (<code>)`.

## 4. Configuration

All settings come from a root `.env` file, which git ignores. `.env.example` is committed with placeholders.

| Variable | Example | Meaning |
|---|---|---|
| `DB_HOST` | `localhost` | SQL Server host |
| `DB_PORT` | `1433` | SQL Server TCP port |
| `DB_USER` | `sa` | SQL login |
| `DB_PASSWORD` | (secret) | SQL password |
| `DB_GLOBAL_NAME` | `TGLOBAL_GSP_TEST` | database holding accounts |
| `DB_GAME_NAME` | `TGAME_GSP_TEST` | database holding characters |
| `JWT_SECRET` | (random, 32+ chars) | signs session tokens |
| `API_PORT` | `3000` | API port |

- The API validates the environment with Zod at startup and exits with a clear message if anything is missing or invalid.
- Database names must match `^[A-Za-z0-9_]+$` and are inserted into queries as bracketed identifiers (`[name].dbo.TACCOUNT_PW`). All values are passed as query parameters.
- The API logs in as `sa` (the user's choice). The API code itself only inserts accounts and reads; it contains no UPDATE or DELETE statements.

## 5. Databases: real vs test copies

**Rule: development, testing and manual checks never write to `TGLOBAL_GSP` or `TGAME_GSP`.**

- Two test databases, `TGLOBAL_GSP_TEST` and `TGAME_GSP_TEST`, live on the same instance. They are created from `COPY_ONLY` backups of the real databases restored under the new names (`scripts/db/create-test-copies.sql`). This only reads the real databases.
- Creating the copies is a separate plan step that runs only after explicit approval.
- Re-running the script refreshes the copies from the current real data.
- During development, `.env` points `DB_GLOBAL_NAME` and `DB_GAME_NAME` at the `_TEST` copies. Pointing them at the real databases is a manual decision for going live.
- **Guard:** `npm run test:db` and any manual verification script refuse to run unless both configured names end in `_TEST`.

## 6. API

All routes are under `/api`.

| Method | Path | Auth | Request | Success |
|---|---|---|---|---|
| POST | `/auth/register` | none | `{ username, password }` | 201, `{ userId, username }`, sets cookie |
| POST | `/auth/login` | none | `{ username, password }` | 200, `{ userId, username }`, sets cookie |
| POST | `/auth/logout` | none | none | 204, clears cookie |
| GET | `/auth/me` | cookie | none | 200, `{ userId, username }` |
| GET | `/characters` | cookie | none | 200, `Character[]` |

### Validation (shared Zod schemas)

- **Username:** 4–16 characters, letters and digits only (`^[A-Za-z0-9]{4,16}$`).
- **Password:** 6–16 printable ASCII characters (`^[\x20-\x7E]{6,16}$`).
- **Register form only:** `confirmPassword` must equal `password`. This is checked in the web form schema, not sent to the API.

### Register

One transaction:

1. `SELECT` the username from `TACCOUNT_PW` with `UPDLOCK, HOLDLOCK`. If it exists, roll back and return 409. Comparison uses the database collation, so it is case-insensitive like the game.
2. `INSERT` into `TACCOUNT_PW` (`szUserID`, `szPasswd` = lowercase SHA-1 hex, `bCheck = 0`) and read the new `dwUserID` with `SCOPE_IDENTITY()`.
3. `INSERT` into `TUSERINFOTABLE` (`dwUserID`, `bCanCreateCharCount = 6`, `bAgreement = 1`). `dCabinetUse` is left to its default (`2008-01-01`).
4. Commit, then sign the user in.

`TACCOUNT_PW` has no unique index on `szUserID` (its only key is `dwUserID`), so the database does not reject duplicate usernames by itself. The `UPDLOCK, HOLDLOCK` check is the only protection: it holds a key-range lock until commit, so concurrent registrations of the same name are serialized and the second one sees the first. The portal does not add an index, because that would change the game's schema.

### Login

- Read `dwUserID`, `szUserID`, `szPasswd` by username.
- Compare the SHA-1 hex of the submitted password to `szPasswd` in constant time.
- Unknown user and wrong password both return 401 with the same message: "Invalid username or password".
- No other checks (bans, IP blacklist): the game enforces those itself.

### Characters

`SELECT` from `TCHARTABLE` where `dwUserID = @userId AND bDelete = 0`, ordered by `bSlot`.

```ts
type Character = {
  id: number;            // dwCharID
  slot: number;          // bSlot
  name: string;          // szNAME
  level: number;         // bLevel
  className: string;     // from bClass
  race: string;          // from bRace
  country: string;       // from bCountry
  money: { gold: number; silver: number; copper: number }; // dwGold, dwSilver, dwCooper
  mapId: number;         // wMapID
  createdAt: string | null;    // dCreateDate, ISO 8601
  lastLogoutAt: string | null; // dLogoutDate, ISO 8601
};
```

### Session

- On login and register the API sets a cookie `session` holding a JWT `{ sub: userId, username }`, signed with `JWT_SECRET`, valid 7 days.
- Cookie flags: `HttpOnly`, `SameSite=Lax`, `Path=/`, no `Secure` (plain HTTP inside the VPN).
- A guard reads the cookie on protected routes and returns 401 if it is missing, invalid or expired.

### Rate limiting

`@nestjs/throttler`, per IP: register 5 per hour, login 10 per minute. Exceeding returns 429.

### Code structure

- `config/`: environment schema and loading.
- `db/`: the `mssql` connection pool (one pool, opened at startup, closed on shutdown) and a helper that runs a function inside a transaction.
- `auth/`: controller, service, JWT cookie guard, SHA-1 helper, and `AccountsRepository` (find by username, create account in a transaction).
- `characters/`: controller, service (maps codes to names), and `CharactersRepository` (list by user).
- `common/`: Zod validation pipe and the global exception filter.

Repositories hold all SQL. Services hold all logic and depend on repository interfaces, so they can be tested with fakes.

## 7. Frontend

### Routes (TanStack Router, file-based)

| Route | Access | Behaviour |
|---|---|---|
| `/` | anyone | Redirects to `/characters` if signed in, otherwise `/login`. |
| `/login` | signed out | Login form. Signed-in visitors are redirected to `/characters`. |
| `/register` | signed out | Register form. On success the user is signed in and sent to `/characters`. |
| `/characters` | signed in | Character list. Signed-out visitors are redirected to `/login`. |

Route guards run in `beforeLoad` using the `me` query from React Query (`ensureQueryData`). The signed-in layout has a top bar with the username and a **Log out** button.

### State

- **React Query:** `me` and `characters` queries; `login`, `register` and `logout` mutations. Login and register update `me`; logout clears the query cache.
- **Theme:** dark only ("Bloodstone"), so there is no client theme state.
- **Forms:** React Hook Form with `zodResolver` and the shared schemas.
- **API helper:** a `fetch` wrapper that sends the cookie, parses JSON, and throws `ApiError { status, message, fieldErrors? }` for non-2xx responses.

### Characters page

One card per character: name, level, class, race, country, money (gold/silver/copper), map number, last logout. States: loading skeleton, empty ("No characters yet. Create one in the game."), error with a retry button.

### Visual design

Tailwind, clean and simple: centered card forms for login and register, and a responsive grid of character cards. A proper visual direction (colours, typography) is chosen before the UI is built, not default Tailwind grey.

## 8. Error handling

### API

| Situation | Response |
|---|---|
| Invalid request body | 400 with field errors from Zod |
| Username taken | 409 |
| Wrong username or password | 401, same message for both |
| Missing, invalid or expired session | 401 |
| Rate limit exceeded | 429 |
| Anything else | 500, generic message |

- A global exception filter shapes every error as `{ statusCode, message, fieldErrors? }`.
- 500 responses never include SQL, table names or stack traces; those are logged to the API console only.
- At startup the API checks the environment and opens the database pool, and exits with a clear message if either fails.

### Web

- A 401 from a protected request clears `me` and redirects to `/login`.
- Field errors show under their fields; other errors (401 on login, 429, 500) show in a message box above the form.
- Submit buttons are disabled while a request is in flight.
- An unknown URL shows a "not found" page with a link home.
- A root error component catches render errors and shows a fallback with a reload button.

## 9. Testing

The default test run (`npm test`) never touches any database.

- **shared:** schema tests for valid and invalid usernames and passwords, including length limits, symbols in usernames and non-ASCII passwords.
- **api:**
  - SHA-1 helper against published test vectors (for example `"abc"` → `a9993e364706816aba3e25717850c26c9cd0d89d`) and lowercase output.
  - Services with fake repositories: register success, taken name; login success, wrong password, unknown user; character code mapping including unknown codes.
  - HTTP tests through the Nest app with fake repositories: status codes 400/401/409/429, cookie set on login and register, cleared on logout, `/characters` rejected without a cookie.
- **api, real database (`npm run test:db`, run manually):** runs the register and character queries against the `_TEST` databases inside a transaction that is always rolled back, including registering the same username twice in one transaction to prove the second attempt is rejected. Refuses to run unless both database names end in `_TEST`.
- **web:** React Testing Library with the API helper mocked: form validation messages, 409 under the username field, 401 in the message box, submit button disabled while pending, route guard redirects, characters page loading, empty, list and error states.

### Manual verification

Against the `_TEST` databases only: register a throwaway account, view characters, log out, log in again. Then check in `TGLOBAL_GSP_TEST` that the new account matches existing ones (lowercase SHA-1 in `szPasswd`, a `TUSERINFOTABLE` row with `bAgreement = 1`). The final proof is logging in to the game with a portal-created account, which happens only after the portal is pointed at the real databases.
