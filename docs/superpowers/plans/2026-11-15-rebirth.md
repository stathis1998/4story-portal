# Rebirth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A level 90 character can pay gold on its portal page to go back to level 1 and carry a lasting stat bonus that the map server applies.

**Architecture:** The portal runs the whole reset as one SQL batch built from its configured table names, against a character that is logged out. Two new game tables hold the rebirth count, the bonus percentage and a log. The map server only reads the percentage at character load (the level freeze pattern) and multiplies the six stats by it. Achievements read the rebirth number and a baseline from the same query as the character's level.

**Tech Stack:** NestJS + mssql + zod (API), React 19 + TanStack Router/Query + Tailwind (web), vitest, SQL Server, C++ (TMapSvr, Visual Studio solution `Server\TServer.sln`).

**Spec:** `docs/superpowers/specs/2026-11-15-rebirth-design.md`. Read it first. The closest existing features: roulette for a money-moving batch and a GM settings page (`apps/api/src/roulette/`, `apps/api/src/games/wallet-bet.ts`, `apps/api/test/db/roulette.db.test.ts`, `apps/web/src/routes/_authed/gm/roulette.tsx`), the level freeze for a section on the character page (`LevelFreezeSection.tsx`, `apps/api/test/level-freeze.http.test.ts`), the wheel for announcements (`apps/api/src/wheel/wheel-announcer.ts`). Copy their patterns unless this plan says otherwise.

## Review Focus

1. **The button is pressed twice, or in two tabs:** one rebirth happens and one price is taken; the second is refused because the character is level 1. (Tasks 2 and 6)
2. **A GM changes the price between the page loading and the player confirming:** nothing is taken, the player is told the price changed and sees the new one. (Tasks 2, 5 and 6)
3. **The character enters the game after the page loaded:** refused naming the reason, nothing written, and the checklist then shows it as in the game. (Tasks 2, 5 and 6)
4. **The awarder runs while a rebirth lands:** no achievement level of the new life is paid from numbers of the old one, such as level 90 or a million kills. (Task 4)
5. **A wallet with loose Silver and Bronze, or exactly the price:** Silver and Bronze are kept to the coin, and a wallet equal to the price ends at zero. (Task 2)

**The tables** (both files use the `IF OBJECT_ID(...) IS NULL CREATE TABLE` form of `TPORTALSETTING.sql`):

```sql
TCHARREBIRTHTABLE    dwCharID INT PRIMARY KEY, bRebirth TINYINT NOT NULL CHECK (bRebirth >= 1),
                     bStatBonus TINYINT NOT NULL CHECK (bStatBonus <= 100), dUpdate DATETIME NOT NULL DEFAULT GETDATE()
TCHARREBIRTHLOGTABLE dwID INT IDENTITY PRIMARY KEY, dwUserID INT, dwCharID INT, szCharName VARCHAR(50), bRebirth TINYINT,

                     bAnnounced TINYINT NOT NULL DEFAULT 0, dRebirth DATETIME NOT NULL DEFAULT GETDATE(),
                     UNIQUE (dwCharID, bRebirth)            -- every column NOT NULL
```

**The batch**, in this order. `SET XACT_ABORT ON`, one transaction, always `COMMIT` and then the result row; a refusal writes nothing. The first check that fails decides the code.

1. Settings: read the four `REBIRTH_KEYS` rows from `portalSettings` with `TRY_CAST(szValue AS INT)`. `REBIRTH_CLOSED` unless live is `'true'` and price is 1 to 100000, percent 1 to 10, limit 1 to 20 and percent times limit is at most 100.
2. Lock the account's rows in `currentUsers` exactly as `walletBetSql` does (`UPDLOCK, HOLDLOCK, FORCESEEK` by `dwUserID`), counting rows with `dwCharID = @charId`.
3. Read the character `WITH (UPDLOCK, ROWLOCK)` by `dwCharID`, `dwUserID`, `bDelete = 0`: none is `REBIRTH_NOT_YOURS`, in the online list is `REBIRTH_ONLINE`, `bLevel < 90` is `REBIRTH_LOW_LEVEL`.
4. `REBIRTH_WEARING` when `characterItems` has any row with `dwOwnerID = @charId AND bOwnerType = 0 AND bStorageType = 0 AND dwStorageID = 254`.
5. Current count from `rebirths WITH (UPDLOCK, HOLDLOCK)` (0 with no row). `REBIRTH_AT_LIMIT` when it is at or past the limit.
6. Price in Gold = (count + 1) times the price setting. `REBIRTH_PRICE_CHANGED` when it differs from `@expectedPriceGold`. `REBIRTH_POOR` when the wallet in Bronze (`gold * 1000000 + silver * 1000 + copper`, in `BIGINT`) is under price times 1000000.
7. The writes:
   - `characters`: `bLevel = 1`; `dwEXP` = `levels.dwEXP` of level 0, or 0 without that row; `wSkillPoint = 200`; `dwHP = 7 * (2 + class.wCON + race.wCON) + 1`; `dwMP = 9 * (2 + class.wMEN + race.wMEN) + 1` (the character's `bClass` in `classChart.bClassID`, `bRace` in `raceChart.bRaceID`); `wSpawnID` = 15001 for `bCountry` 0, 15002 for 1, else 15003; `wMapID`, `fPosX`, `fPosY`, `fPosZ` from that `spawnPositions` row (`THROW 50000, 'Start point missing', 1` without it); `wLastSpawnID = 0`, `dwLastDestination = 0`, `dwRegion = 0`, `bAftermath = 0`; the wallet minus the price, split as `walletBetSql` splits it.
   - `skills`, for rows whose `skillChart.bKind <> 0` only: rows in `startSkills` for the character's class get that row's `bLevel`; rows not in it are deleted. Then insert every `startSkills` row of the class the character lacks, with `dwRemainTick = 0`. Rows with `bKind = 0` or no chart row are untouched.
   - `hotkeys`: for N from 1 to 12, set `bTypeN = 0, wIDN = 0` where `bTypeN = 1` and the character has no `skills` row for `wIDN` with `bLevel > 0`. Generate the twelve column pairs in TypeScript.
   - Delete the character's rows in `skillMaintains`, `quests`, `questTerms`, `levelFreezes`.
   - `allCharacters`: `bLevel` and `dwEXP` as above, by `dwCharID` and `dwUserID`.
   - `rebirths`: insert or update to the new count, `bStatBonus` = min(count, limit) times percent, `dUpdate = GETDATE()`.
   - `rebirthLog`: one row; `szText` is `@text` with `{name}` and `{rebirth}` replaced; `SCOPE_IDENTITY()` is the result's `id`.

- Produces these routes, all behind `SessionGuard`:

| Route | Body | Returns |
|---|---|---|
| `GET characters/:id/rebirth` | | `RebirthState` |
| `POST characters/:id/rebirth` (200, throttled 10 a minute) | `RebirthRequest` | `RebirthState` after the rebirth |

`GmRebirth.recent` is the newest 20 log rows. `RebirthState`: `open` is `rebirthIsOpen(settings)`; `bonus` is the saved `bStatBonus`; `next` is null when `rebirths >= limit`, else `{ number: rebirths + 1, bonus: rebirthBonus(rebirths + 1, settings), priceGold: rebirthPriceGold(rebirths + 1, settings.priceGold) }`.

Refusals, exact copy:

| Code | Status | Message |
|---|---|---|
| `REBIRTH_NOT_YOURS`, or `find` returns null | 404 | `Character not found` |
| `REBIRTH_CLOSED` | 409 | `Rebirth is closed right now` |
| `REBIRTH_ONLINE` | 409 | `Log out of the game with this character first` |
| `REBIRTH_PRICE_CHANGED` | 409 | `The price has changed. Check it and confirm again` |
| `REBIRTH_LOW_LEVEL` | 422 | `This character is not level 90 yet` |
| `REBIRTH_WEARING` | 422 | `Take off everything this character is wearing first` |
| `REBIRTH_AT_LIMIT` | 422 | `This character has reached the rebirth limit` |
| `REBIRTH_POOR` | 422 | `This character does not have enough Gold` |
| `freshBaseline` returns null (the batch is not called) | 503 | `Rebirth is not available right now. Try again in a minute` |

Before the full stats load the service refuses from the `find` row and the settings what it can: closed, online and under level 90, with the codes above. The batch checks everything again and stays the authority.

The log line passed as `text`: `{name} was reborn (rebirth {rebirth})`. The baseline passed is `JSON.stringify(await stats.freshBaseline(id))`; a null baseline is the 503 above, never `{}`, which would pay every counter again. After a rebirth the service calls `stats.dropCache()`.
